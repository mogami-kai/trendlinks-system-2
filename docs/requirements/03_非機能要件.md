# 03. 非機能要件（NFR）

## 3.1 性能
- 主要画面の初期表示は通信良好な 4G/Wi-Fi 環境で 2.5 秒以内（LCP 目安）。
- 一覧 API レスポンスは 100 件ページングで 500ms 以内（p95、通常負荷時）。
- 画像はクライアントでリサイズ/圧縮（長辺 1600px 程度）してからアップロード。
- Next.js の RSC / 画像最適化 / キャッシュを活用し転送量を最小化。

## 3.2 可用性・信頼性
- Supabase / Vercel のマネージド SLA に準拠（基本構成で十分な可用性）。
- 障害時もデータはマネージド DB に永続化。日次自動バックアップ（Supabase）。
- 外部連携（LINE/Stripe/Brevo）失敗時はリトライ・ログ記録・フォールバック。

## 3.3 セキュリティ
- 認証は Supabase Auth（JWT）。詳細は `07_認証認可.md`。
- **マルチテナント分離は RLS で強制**（アプリ層のみに依存しない）。
- 機密値（Service Role Key・Stripe Secret・LINE Token 等）はサーバー環境変数のみ。
  クライアントに露出する値は `NEXT_PUBLIC_` の anon key 等に限定。
- 通信は全て HTTPS。Storage は署名 URL でアクセス制御。
- Stripe Webhook は署名検証。LINE Webhook も署名検証。
- 個人情報（スタッフ・顧客・現場住所・位置情報）は最小権限で取扱い、`11` に準拠。
- 入力バリデーション（クライアント + サーバー両層）、XSS/CSRF 対策。
- 依存パッケージの脆弱性監査（`npm audit` / Dependabot）。

## 3.4 スケーラビリティ
- サーバーレス（Vercel）+ マネージド DB（Supabase）で水平スケール。
- 想定: 1,000 テナント規模（資料の MRR 試算）でも構成変更不要を目標。
- DB はテナント単位のインデックス設計（`tenant_id` 複合インデックス）。

## 3.5 ユーザビリティ / レスポンシブ
- **スマホ完結 UX** を最優先（タップ領域・片手操作・大きな CTA）。
- Tailwind CSS（emerald カラー）でブランド統一。
- タブレット・PC でも崩れないレスポンシブ。
- 主要動線（到着 → 報告 → 写真 → 提出）を最短ステップに。
- アクセシビリティ: コントラスト比 WCAG AA 目安、フォーカス可視化。

## 3.6 国際化
- 初期は**日本語のみ**。文言は将来の i18n を見据えメッセージ集約を推奨。
- 日時は JST、通貨は円（¥）表記。

## 3.7 ブラウザ・端末対応
- モバイル: iOS Safari / Android Chrome（最新 2 メジャー）。
- デスクトップ: Chrome / Edge / Safari / Firefox（最新 2 メジャー）。

## 3.8 保守性・運用性
- TypeScript による型安全、ESLint/Prettier、テスト（`12` 品質ゲート）。
- 構成のコード化（Supabase migrations、Vercel 設定）。
- ログ/監視: Vercel ログ、Supabase ダッシュボード、Stripe/LINE 連携監視。
- **月次運用工数 4-8 時間**（顧客サポート・ログ確認・通知監視・更新反映）を想定。
- **月次運用コスト 約 ¥3,000**（従量課金・初期費用なしの軽量構成）を目標。

## 3.9 法令・コンプライアンス
- 個人情報保護法に準拠。個人情報保護管理者を代表者として明示（`11`）。
- 特定商取引法に基づく表記を整備（`11`）。
- GPS/位置情報の取得は利用目的を明示し同意取得。
